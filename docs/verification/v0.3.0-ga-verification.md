# turna — GA verification (v0.3.0)

Records the verification behind the **v0.3.0 Production GA** promotion, dated
2026-07-14. Environment: Linux (x86_64), Tarantool 2.11.5, Rust workspace built
with `--all-features` (`io-uring, af-xdp, dtls, web-transport`).

Scope note: this document covers the **code-level** GA gates verified in this
pass. The earlier live / endurance / interop / failover / scale / DTLS evidence
from the RC cycle is retained, unchanged, in
`docs/verification/pre-GA-status.md` (a dated `v0.3.0-rc.1` snapshot) and is not
repeated here.

## 1. Code-level verification (this pass)

| Gate | Result |
| --- | --- |
| `cargo fmt --all -- --check` | passed |
| `cargo test --workspace --all-features` | passed |
| `cargo clippy --workspace --all-targets --all-features -- -D warnings` | passed |
| Tarantool TAP — `migration_cas_test` | 12 / 12 |
| Tarantool TAP — `u64_parser_test` | 22 / 22 |
| Tarantool TAP — `version_cas_roundtrip_test` | 5 / 5 |

The RC-era "Unreleased GA implementation gates" are now exercised by the
workspace test suite and the Tarantool stored-procedure TAP suites:

- node-targeted `update_config`; stale expected-version conflict;
- idempotent retry after response loss **and** after command-log GC;
- runtime and user-limit restart restore;
- concurrent Allocate at user limit 1; rollback on later reservation failure;
- bandwidth / lifetime updates;
- bounded / resumable three-phase Tarantool migration with page-CAS, a
  monotonic lease fencing generation, canonical Rust payload hashing, and
  partial / orphan-row handling;
- exact-u64 versioning (runtime, user-limits, fencing token) with overflow
  refused, verified across the `2^53` and `u64::MAX` boundaries;
- atomic observed confirmation — the idempotency journal write and the
  observed-state update commit in one `box.atomic` transaction (rollback of both
  on a failed observed write is covered by TAP);
- fail-closed outcome recording (write + read-back both failing → retry, no
  completion);
- gossip leave / rejoin (in the `turna-cluster` unit suite).

## 3. Remaining before full production sign-off

Not covered by this code-level pass; owned by `RELEASE.md`:

- admin frontend build (`npm ci && npm run build`);
- node + admin container builds, and the admin container smoke;
- Helm lint / template and a standalone deployment;
- cluster failover smoke — induced node-death / ownership failover;
- release rollback drill.

External / process (unchanged from the RC assessment): real-network **UDP**
load from an unfiltered external generator; multi-week staging with real
traffic; alert-threshold calibration; an independent external security audit /
pentest; full allocate-over-DTLS by a live client; admin stage-2 in a deployed
(mTLS / exposed) posture.

## 4. Feature scope

The **standalone Tokio core** (STUN/TURN, auth, limits, durable runtime config,
management plane, single-node persistence) is **Production GA**. Optional
subsystems remain **experimental / preview** and are not promoted by this
document: `io-uring`, `af-xdp`, `dtls`, `quic`, `web-transport`, TLS-over-TCP,
RFC 6062 TCP relay, and multi-node cluster / gossip mode.
