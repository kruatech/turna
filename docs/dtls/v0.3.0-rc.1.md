# DTLS (TURN over DTLS) — v0.3.0-rc.1

Verification of the DTLS transport (TURN over DTLS, RFC 7350), built behind the
`dtls` feature (`webrtc-dtls` 0.10). DTLS is a low-priority transport for GA:
browsers do not use TURN-over-DTLS (WebRTC uses `turn:`/`turns:`), so this is
"prove the transport is live and correct", not a production client path.

## What was verified

- **Builds.** `cargo build --release -p turna-node --features "tls dtls"` is
  green; `webrtc-dtls` compiles and links.
- **Listener starts, fail-closed config.** `spawn_dtls` validates `[turn.dtls]`
  (`validate_dtls`: non-zero port, cert/key are regular files, idle_timeout > 0,
  MTU 576–65535) and aborts startup if enabled-but-misconfigured. Bounded
  per-session outbound queue, per-IP session cap, MTU capping, session stats.
- **DTLS handshake works with the operator cert.** With the Let's Encrypt cert
  for `turna.krutilin.pro` (key converted to PKCS#8), `openssl s_client -dtls
  -connect …:5349` completes:
  - `Protocol: DTLSv1.2`
  - `Cipher: ECDHE-ECDSA-AES128-GCM-SHA256`
  - `subject=CN=turna.krutilin.pro`, `issuer=Let's Encrypt`
  - `Verify return code: 0 (ok)`
- **TURNS (TCP) and DTLS (UDP) coexist on :5349** — different transports on the
  same port, both serving the same operator cert, no conflict.

## Certificate requirements (important)

`webrtc-dtls` is stricter than the TLS (rustls) path:

- **Key must be PKCS#8** (`-----BEGIN PRIVATE KEY-----`), not SEC1
  (`-----BEGIN EC PRIVATE KEY-----`). Let's Encrypt / Caddy emit SEC1 by
  default; convert:
  `openssl pkcs8 -topk8 -nocrypt -in key.pem -out key.pk8.pem`.
- **Key must be ECDSA P-256.** `webrtc-dtls` negotiates only `ECDHE-ECDSA-*`
  suites; an RSA cert loads but every handshake then aborts with
  `internal_error` (no shared cipher).
- The rustls TLS path accepts SEC1 and RSA, so a cert that works for TURNS may
  not work for DTLS — this asymmetry is now explicit.

## Fail-closed fix (this cut)

Previously, if a DTLS cert/key was configured but failed to load (e.g. a SEC1
key), the listener silently fell back to an ephemeral self-signed cert with a
WARN — the operator would believe DTLS served their cert when it did not.
Changed (`crates/transport/src/dtls.rs`, `load_certificate`): an ephemeral cert
is used ONLY when no cert/key is configured (dev/test). If a cert IS configured
and fails to load, the node now logs an ERROR with the exact fix and refuses to
start (fail-closed), matching the TLS path.

## What was NOT verified

- **Full allocate-over-DTLS by a live TURN client.** No common DTLS-TURN client
  exists (`turnutils_uclient`'s OpenSSL DTLS stack does not interoperate with
  `webrtc-dtls`, mirroring the TURNS/turnutils incompatibility; browsers do not
  do TURN-over-DTLS). The STUN/TURN protocol layer is transport-independent and
  is verified over UDP and TURNS (allocate, auth, relay), so the risk that
  allocate is broken specifically over DTLS is low — but it is not directly
  exercised here.
- To close this fully, a small custom DTLS-TURN probe would be needed
  (`webrtc-dtls` client `Conn::new(sock, is_client=true, …)` + the existing STUN
  Allocate logic from `tools/load-test/src/turn_client.rs`). Deferred until
  there is real demand for TURN-over-DTLS.

## Status

Transport and handshake: verified. Config safety: fail-closed. Cert
requirements: documented. Full TURN allocate over DTLS: deferred (niche, no
client, transport-independent STUN layer already verified elsewhere).
