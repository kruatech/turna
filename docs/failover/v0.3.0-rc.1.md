# Failover drill — v0.3.0-rc.1

Live multi-node failover verification on Linux (x86_64, Docker), against a real
Tarantool state backend. This is the drill that closed audit item #7 and
uncovered/fixed a P1 that unit tests could not catch.

## Topology

- Tarantool 3.x (`turna-tnt`, 172.30.0.2:3301), schema from
  `deploy/tarantool/init.lua`, dedicated `turna` user, `turna_app` role.
- Two nodes (`turna:rc-test` image), cluster mode, gossip + Tarantool backend,
  `[cluster.persistence] mode = write_behind`:
  - node-a2 — 172.30.0.10
  - node-b2 — 172.30.0.11 (gossip seed → node-a2)
- Shared cluster secret (gossip HMAC authenticated).

## P1 found: list stored-functions truncated to one row

Symptom: with two nodes on a real Tarantool cluster, killing the owner node did
not trigger adoption. `failover_claimed_total` stayed 0; the sweep logged
`confirmed-dead dead_count=1` while `orphans_seen=0`.

Root cause: the Lua list functions in `init.lua` returned `return unpack(res)`
— a flat multiple-return. Over iproto CALL this was serialised so the Rust
`parse_call_data` (which expects the CALL wrapper `[[...]]`) saw only the first
element and truncated the result to a single row. This silently broke every
list read on the Tarantool backend: `find_by_node`, `get_live_nodes`,
`find_by_user`, `find_expired`, `list_allocations`, `list_users`,
`load_active_revocations`.

Consequence for failover: the sweep's `get_live_nodes` saw one node instead of
all, so the dead set was wrong; even when a dead node was identified,
`find_by_node(dead_id)` returned <=1 orphan. Adoption never completed.

Why unit tests missed it: the in-memory backend does not use iproto/Lua at all
(native Rust `get_live_nodes`), and the Tarantool integration tests exercised
the CAS primitive (`claim_allocation`) directly rather than through the
list-returning sweep path. Only a live multi-node run against real Tarantool
surfaced it.

## Fix

`deploy/tarantool/init.lua`: all seven list functions changed from
`return unpack(res)` to `return res` (return one array value). This matches the
contract `parse_call_data` already implements ("unwrap the extra array layer
that CALL adds"), so the full row set is returned.

Regression guard: `integration_list_functions_return_all_rows_not_truncated`
in `crates/state-backend/src/tarantool.rs` stores five rows under one node and
asserts `find_by_node` returns five (pre-fix: one). Runs in CI's
`failover-integration` job against a real Tarantool.

Schema note: `init.lua` creates stored functions with `if_not_exists = true`,
so they are NOT recreated with the new body on an existing Tarantool instance.
Existing deployments must drop and recreate the affected functions (or reload
the schema) when upgrading. Fresh installs pick up the fix automatically.

## Drill result (post-fix)

1. node-a2 stopped; three allocations created on node-b2 (owner) — persisted to
   Tarantool with node_id = node-b2 (tarantool_writer_ops_total = 3).
2. node-a2 restarted; cluster reformed (topology nodes=2); node-a2 loaded no
   foreign allocations at startup (bulk-load fetches own node only).
3. docker kill turna-b2.
4. node-a2 detected node-b2 dead via the backend heartbeat path (live_window 3s
   + suspicion debounce), independently of the slower gossip timeout:
   - t=3s: claimed=0
   - t=6s: claimed=3   <-- adoption
5. Final state:
   - failover_claimed_total = 3, failover_lost_race_total = 0,
     failover_errors_total = 0 (no split-brain).
   - All three allocations in Tarantool moved from node-b2 to node-a2
     (verified via list_allocations).

## DoD — met

- before kill: allocations owned by node-b2 — yes
- after kill: surviving node performed CAS adoption — yes
- failover_claimed_total increased — yes (0 -> 3)
- backend owner changed — yes (node-b2 -> node-a2, all 3)
- no split-brain — yes (lost_race = 0, errors = 0)

## Notes / limitations

- Drill ran with TURNA_ALLOW_LOOPBACK_PEERS=1 (dev-only) so the local test
  client could relay to loopback peers. Production keeps the peer filter strict.
- turnutils_uclient does not follow 300 Try Alternate and does not refresh,
  so it was only used to create allocations on the owner (determined by
  temporarily running a single node); it did not keep them live via refresh.
- Clock skew between nodes is a known limitation of the failover live-window
  logic (documented in services/node/src/failover.rs): NTP-class (<1s) skew is
  tolerated; large skew can misclassify liveness. Ensure NTP on cluster hosts.
