# Scale test — v0.3.0-rc.1

Store-layer behaviour with 50,000 allocations owned by a single node, against a
live Tarantool 2.11, using realistic full-JSON allocation blobs (~458 bytes
each, all StoredAllocation fields incl. permissions/channels). Verifies that the
indexed access paths do not degrade at scale and characterises the cost of
failing over a large node. Closes the scale item for the RC → GA checklist.

## Setup

- Tarantool 2.11 (Docker), schema from `deploy/tarantool/init.lua` (P1-fixed).
- 50,000 rows in `turna_allocations`, all owned by `node-scale`, each `data`
  field a full JSON allocation (~458 bytes; 50k × 458 B ≈ 23.7 MB total).
- Measurements taken locally inside Tarantool (no iproto/network round-trip),
  so they isolate the backend cost; see "Real-world caveat" for the network
  correction.

## Results

| Operation                     | Result                        | Notes |
|-------------------------------|-------------------------------|-------|
| `count_allocations`           | 0.02 ms                       | `space:len()`, O(1), independent of size |
| `list_allocations(0, 100)`    | 0.10 ms                       | pagination (offset/limit) bounds the scan |
| `find_by_node` (all 50k)      | 84 ms, 50,000 rows, 23.7 MB   | `by_node` index; returns the full set (no limit) |
| `claim_allocation` × 50k      | 3,147 ms (0.063 ms/claim)     | JSON decode + node_id rewrite + CAS per row |

## Interpretation

Indexed access scales well. `count` is O(1); `list` with a limit is instant;
`find_by_node` returns all 50k rows (23.7 MB) in 84 ms via the `by_node` index.
The store layer is fine at 50k (which is also the node's configured
`max_alloc = 50000`, i.e. a single node's practical ceiling).

The meaningful cost is **failing over a large node**:

- Enumerating the dead node's orphans (`find_by_node`) is cheap: 84 ms.
- Reassigning them is a *sequential* `claim_allocation` CAS per row. Locally
  50k claims take ~3.1 s. This is by design — correctness (one CAS per row,
  exactly-one-winner) is favoured over batch speed.

### Real-world caveat

These are local (in-Tarantool) numbers. In production the failover sweep issues
each `claim_allocation` over iproto (Rust → Tarantool), so a per-claim network
round-trip is added to all 50k claims. At ~0.2–0.5 ms RTT that is roughly
10–25 s on top, and the Rust side must also parse the 23.7 MB `find_by_node`
response (50k `StoredAllocation`) into memory. **Realistically, failing over a
node holding 50k allocations takes on the order of tens of seconds**, dominated
by the sequential claim loop and the response parse.

This is acceptable for a rare event, but the time scales linearly with the
number of allocations on the failed node.

## DoD — met

- Indexed reads (`count`, `find_by_node`, `list`) do not degrade at 50k.
- Pagination bounds `list_allocations`.
- Failover of a large node is correct (all 50k reassigned) and its cost is
  quantified.

## Limitations / recommendations

- `find_by_node` has no limit — it returns the whole set. At 50k that is 23.7 MB
  in one response, parsed fully into Rust memory (also at node startup via
  `bulk_load`). Fine at 50k; for 100k+ per node, streaming/pagination on this
  path would be worth adding.
- Failover time grows linearly with allocations-per-node. Keep per-node
  allocation counts within a few thousand for fast failover, or accept that a
  very large node takes tens of seconds to be adopted.
- Numbers are single-node, single-Tarantool, local timing. Multi-node
  contention and real-network load are separate items.
