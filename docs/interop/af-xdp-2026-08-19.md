## Scope — read this before quoting the result

**This is a veth pair, not a NIC.** It exercises the frame path, the XDP attach, the
UMEM rings, ARP/NDP handling and the relay logic. It does not exercise a real driver,
which is the entire reason AF_XDP exists: the attach lands in SKB (generic) mode
because veth offers no native XDP here, so every frame is copied and none of the
kernel-bypass benefit is present.

A pass here means the datapath is **correct**. It says nothing about whether it is
fast on the hardware you deploy. Numbers from this lab are not capacity figures.

## Lab requirements that are not obvious

**The peer must live in its own network namespace.** `scripts/lab/af_xdp_veth_setup.sh`
puts both ends in the host namespace, and that cannot work: with `10.123.0.1` and
`10.123.0.2` both local to one stack, the kernel short-circuits through `lo` and the
traffic never crosses the veth. Proven directly —

```
$ ip route get 10.123.0.1 from 10.123.0.2
local 10.123.0.1 from 10.123.0.2 dev lo
```

— and the symptom was `rx_frames_total = 0` together with `parse_drops_total = 0`, i.e.
not "dropped after parsing" but "never arrived". `scripts/verify/af-xdp-lab.sh` builds
its own namespace and refuses to start if the route does not leave via the veth.

**`frame_count` must not exceed twice the ring size.** `af_xdp.rs` honours
`frame_count` but pins the rings to the library defaults (2048), and the RX half of the
UMEM has to fit the fill ring:

| `frame_count` | `umem_free_frames` | RX |
|---|---|---|
| 4096 (default) | 2016 | works |
| 16384 | 8160 | **dead, 0 frames, no error anywhere** |

Related and worth fixing: `[turn.af_xdp]` exposes `fill_ring_size`, `comp_ring_size`,
`rx_ring_size` and `tx_ring_size`, and all four are ignored. A key that does nothing
invites exactly the change that breaks RX.

**Pin the neighbour entries.** The XDP program redirects all ingress into the xsk, so
the kernel's ARP responder on the node's interface is bypassed and the datapath answers
ARP itself.

## The bug this run found: RX leaked its frames

`recv_batch` took the descriptor buffer for `poll_and_consume` out of `free_frames`
— the TX pool. `poll_and_consume` overwrites the first `n` entries with descriptors
pointing at the frames the kernel filled from the fill ring, so those `n` were
correctly returned to the fill ring while the `n` frames drained from the pool had
their addresses destroyed and were returned nowhere.

Every receive batch permanently consumed `n` frames. Once the pool emptied, `want` was
0 and `recv_batch` returned without even polling — RX stopped for good.

The evidence was unusually clean: `rx_frames_total` came out as **exactly 2015 in three
runs at different rates and durations**, against a pool of 2016. Congestion does not
produce a constant. 604 frames passed losslessly, 2404 lost 43 %, and
`umem_free_frames` finished at 0.

A second, smaller leak sat in the same lines: `fill.produce()` returns how many
descriptors it actually placed, and the result was discarded, so anything a full ring
refused was dropped on the floor.

**Fix:** a dedicated `rx_scratch` buffer that the RX ring overwrites — the same pattern
already used for `comp_scratch` a few lines above — and refused descriptors stay in the
scratch to be offered again. RX frames now live in the fill ring, TX frames in the
pool, and the two no longer trade places. Result: 7123 frames received with zero loss
where the ceiling used to be 2015.

**This is the second leak of exactly this shape today.** The io_uring datapath went
deaf after precisely 64 relayed packets because the zero-copy path never re-armed its
recv slot (`docs/soak/endurance-2026-08-19.md`). Both were invisible to every existing
check, both showed up as a hard stop at a pool or slot count, and both were found by
comparing a counter against the size of the thing it was exhausting.

**And `umem_free_frames` was no help.** It reads the TX pool, which is why it sat at a
healthy 2016 while the receive path starved. Now documented as such.

## Cold start

The first probe of a run failed while every later one passed — a single lost packet, and
the conformance probes send one request each with no retry. Fixed by having the lab wait
for the datapath to signal readiness rather than firing as soon as `/ready` answers.
Waiting is the right fix; adding a retry to the client would have hidden it.
