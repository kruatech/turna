# Browser WebRTC interop — v0.3.0-rc.1

Real-browser WebRTC interop verification against turna over TURNS
(TURN-over-TLS), using a live public domain with a trusted Let's Encrypt
certificate. Exercises the production path a real client takes: browser →
public IP → turna → relay. Closes the browser-interop and TURNS items for the
RC → GA checklist, and confirms the REQUESTED-ADDRESS-FAMILY fix against a real
browser.

## Setup

- Server: turna-node built with `--features tls`, running on a public host.
- TURNS listener on :5349 (TURN over TLS-over-TCP), `enable_alpn` (stun.turn).
- Certificate: Let's Encrypt for `turna.krutilin.pro`, issued and renewed by
  Caddy; turna reads the PEM cert/key directly (hot-reload by mtime).
- `external_ip = 85.192.158.8` (public), relay port range narrowed to
  49152-49161 (10 ports), forwarded on the router (UDP) for relay media.
- Router port-forwards: 80/tcp (ACME), 5349/tcp (TURNS), 3478/udp (TURN),
  49152-49161/udp (relay media).
- Clients: Chrome 150, Firefox 152, Safari 26.5 on macOS — all three passed
  5/5 (see per-browser note below). Standalone single-file WebRTC interop tester
  (RTCPeerConnection, iceTransportPolicy relay-only, REST ephemeral creds
  = base64(HMAC-SHA1(shared_secret, "expiry:name"))).
- Config URI: `turns:turna.krutilin.pro:5349?transport=tcp`.

## Results — 5/5 PASS

### T1 — Allocate / relay candidate — PASS
Relay candidate received in 338 ms; relay address 85.192.158.8:49152. A real
browser WebRTC stack allocated through turna over TURNS with a trusted cert.

### T2 — Auth negative — PASS
With deliberately invalid credentials the browser logged
`icecandidateerror code=401 Unauthorized` and no relay candidate was issued.
This is a genuine rejection by the server (a real 401 over TLS), not a timeout —
authentication is enforced on the TURNS path.

### T3 — End-to-end relay data-channel — PASS
Two peer connections, both relay-only, exchanged 50/50 echo messages through the
relay (147 ms wall). getStats confirmed the active candidate pair is
relay/relay on both sides (local=relay/udp remote=relay), RTT ~150 ms, real
bytes transferred (A sent 6472 / recv 4956; B sent 4956 / recv 5072). Media data
actually flows through turna's relay over the public path, not just signalling.

### T4 — Transport TLS — PASS
Relay candidate over the `tls` transport received in 323 ms; address
85.192.158.8:49157. TURNS transport confirmed independently of T1.

### T5 — Address-family (indirect) — PASS
Allocate succeeded in Chrome 150, which means turna correctly handled
REQUESTED-ADDRESS-FAMILY (0x0017) and did NOT answer 420. Live confirmation, by
a real browser, that the RAF fix does not break the browser allocate path.

## What this closes

- Real-browser WebRTC interop (was a GA blocker) — confirmed with Chrome 150.
- TURNS (TLS path) — confirmed end-to-end, including relay data transfer.
- REQUESTED-ADDRESS-FAMILY fix — confirmed in the field by a real browser.
- Public production path (browser from the internet → public IP → turna →
  relay) — confirmed working, including router-forwarded relay media ports.
- REST ephemeral credential scheme — confirmed interoperable with the browser's
  WebRTC credential handling.

## Browser matrix

All three major WebRTC engines passed 5/5 over the same TURNS config
(`turns:turna.krutilin.pro:5349?transport=tcp`, trusted LE cert):

- Chrome 150 (Blink): allocate 338 ms, e2e relay 50/50, TLS, RAF.
- Safari 26.5 (WebKit): allocate 369 ms, e2e relay 50/50, TLS, RAF.
- Firefox 152 (Gecko): allocate 295 ms, e2e relay 50/50, TLS, RAF.

Firefox note: with `network.proxy.type = 5` (use-system-proxy) Firefox
routed WebRTC through a system proxy/VPN that did not pass TURNS, so ICE
gathering timed out. Setting it to `0` (no proxy) made Firefox pass 5/5.
This is a Firefox client/proxy configuration issue, not a turna defect —
Chrome and Safari, which did not route through that proxy, passed as-is.

## Limitations / notes

- Trusted cert path: turna reads a copy of the Let's Encrypt cert issued by
  Caddy. For production, wire turna to read the live cert (group-readable, or a
  refresh hook) so renewals are picked up automatically; turna's mtime
  hot-reload supports this once the file path is stable and readable.
- Plain UDP TURN (turn:...:3478) from the tester's VPN path could not be
  verified because that particular VPN does not pass UDP to the server; this is
  a client/VPN limitation, not a turna issue (the public path via the external
  IP works, as T1–T4 over TURNS and the relay-media UDP ports demonstrate).
- DTLS transport (TURN over DTLS) is implemented but not exercised here; it is
  not the path browsers use and is out of scope for this verification.

## Mobile & multi-OS (external network, TCP/TLS)

Extended the interop run to mobile and additional desktop OSes, all over the
external network (clients reached `turna.krutilin.pro` over the public internet;
the single-file tester was served over HTTPS from the node behind Caddy + a
trusted LE cert). Transport was TCP/TLS throughout
(`turns:turna.krutilin.pro:5349?transport=tcp`) — UDP is not reachable from
outside this network (ISP/CGNAT drops inbound UDP; see the scale/verification
notes), so the browser path deliberately uses TURNS-over-TCP, which is the
common production case behind restrictive NATs anyway.

Devices / browsers, each 5/5 (allocate, auth-negative, e2e relay, TLS
transport, RAF):

- iPhone — Safari (WebKit, iOS) and Chrome (iOS).
- Android — Chrome (Blink) and Firefox (Gecko).
- iPad — Chrome (iPadOS).
- Windows — Chrome (Blink).
- Linux — Chrome (Blink).

Networks exercised: home Wi-Fi and mobile (4G/5G) on the phones; external for
all. Mobile 4G/5G also uses TCP/TLS — inbound UDP is dropped on the mobile path
as well, consistent with the fixed-line result.

### What this adds

- Mobile WebRTC engines (iOS WebKit, Android Blink/Gecko) confirmed against
  turna over real networks — previously untested.
- Multiple OSes (iOS, iPadOS, Android, Windows, Linux, plus the earlier macOS)
  — broad client coverage for the TURNS/TCP path.
- Reconfirms the UDP limitation is a network-path (ISP/CGNAT) property, not a
  turna defect: TCP/TLS works from every client and network tried; external
  UDP does not arrive on any of them.
