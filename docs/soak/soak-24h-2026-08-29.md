# 24-hour soak — 2026-08-29

**PASS. No leak.**

The first 24-hour soak in this project to reach a verdict. Three earlier attempts
are still on disk in `turna_old` as ~9 GB directories each: they filled the disk
and stopped, and nobody noticed that the runs behind the stability claim had never
finished.

| | first idle floor | last idle floor |
|---|---|---|
| RSS | 18 MiB | 18 MiB |
| File descriptors | 18 | 18 |
| Threads | 6 | 6 |

Across 24 hours: **824 083 157 allocations**, **5 795 759 332 packets received**,
373 GB in, 410 GB out. Zero processor panics. Parser rejections, malformed packets
and peer rejections all flat at zero.

## The three warnings, explained

The verdict flagged 22 warnings. All of them reduce to two causes.

### 18 % errors in every `allocate` phase — the rate limiter, not the node

Twenty-one cycles, each reporting almost exactly 18 % errors on the `allocate`
driver, while `channel-data` reported zero and `binding` 0.04 %.

That consistency is the tell: a degradation drifts, a limit does not.

`rate_limited` finished at **10 741 513** with `quota_exceeded` at **0**. The soak
runs `allocate --concurrency 400` from a single source address, and
`TieredLimits::allocate` is 32 per second per source IP with a burst of 16. So
roughly one in six attempts is refused, every cycle, by design.

The node behaved correctly. What the run measured, in those phases, was the
limiter.

This is the same effect that made a load test report "8 allocations is what this
host sustains" earlier in this work, when the host in fact sustained 38 — the
difference being source addresses. The load tool has `--source-ips` for exactly
this; the soak script does not use it.

**Worth fixing in the soak**, because 18 % of the allocate phases is 18 % of the
work not reaching the code under test. Not urgent: the `channel-data` phases carry
the relay path at zero loss, which is the part a soak is for.

### 467 egress drops, once, in one sample

All 467 appeared in a single sample at t=3893 s — the **last load sample of cycle
3**, immediately before the idle phase. The counter did not move again for the
remaining 23 hours, across twenty more such transitions.

Reading the samples either side:

```
3862  load  alloc=400  drops=0
3893  load  alloc=400  drops=467   <- last load sample
3923  idle  alloc=0    drops=467
```

Four hundred sessions closing at once. Frames already queued for peers that were
gone by the time the queue drained.

**Not capacity, and not a leak.** Eight drops per hundred million packets, once,
at a session teardown — and RSS did not move (18 276 → 18 360 KiB, ordinary
noise).

A frame addressed to a session that no longer exists has nowhere to go, so
dropping it is right. The imprecision is in the counter rather than the behaviour:
`turna_send_queue_dropped_total` reads as "the node could not keep up", and this
was "the recipient left". Separating the two would need a second counter, and the
existing one is already documented as something to alert on — changing its meaning
before a release is the wrong order.

Recorded so that a future run showing a handful of drops at a phase boundary is
recognised rather than investigated from scratch.

### `auth_failures` at 31.5 million — the 401 handshake, not a problem

Expected, and worth writing down because the number looks alarming.

RFC 5389 long-term credentials require the client to send an unauthenticated
request first, receive `401` with a realm and nonce, and only then sign. Every
allocation therefore produces one "auth failed" before it produces a success. At
824 million allocations, 31.5 million such events is *fewer* than one per
allocation — the driver reuses nonces where it can.

**But the node logs each one at WARN.** At the soak's rate that produced 4.8 GB
per hour of log — enough that the first attempt at this run filled 50 GB of disk
before the level was dropped to `warn`, and even then the file had to be truncated
by a watchdog.

A mandatory step of the protocol should not be a warning. Logging it at DEBUG,
and keeping WARN for a failure *with* credentials — which really does mean a wrong
password — is the fix. Deferred: it changes logging behaviour, which is not
something to introduce immediately before a release.

## What this run also established, incidentally

**The soak could not previously complete.** It generated its config with no
logging section, so the node inherited `TelemetryConfig::default()`'s
`"info,turna=debug"` — every module at DEBUG. 4.3 GB in 13 minutes. The three
abandoned 9 GB directories in `turna_old` are what that looks like from the
outside.

Now: `RUST_LOG` set explicitly, a disk-budget check that refuses up front rather
than failing at hour twelve, and a size cap on `node.stdout`.

**The budget estimate was wrong by a factor of twenty.** I guessed 300 MB per
hour; the measurement was 4.8 GB at INFO and about 7 GB at WARN before the
truncation watchdog took over. The check would have admitted a run that dies
halfway. Corrected against the measurement.

## What this run does not establish

**Anything about the DTLS demux path.** The soak has no DTLS parameters and ran
the tokio datapath over UDP. The demux path has nine checks over five minutes and
no long run, which is why the default has not been flipped.

**Anything about a real network.** Loopback, one host, driver and node sharing 32
threads.

**Anything about a cluster.** Single node, no backend.
