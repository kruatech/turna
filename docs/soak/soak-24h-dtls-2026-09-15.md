# 24-hour soak — DTLS demux on `crates/dtls`, 2026-09-15

**Verdict: PASS, with 17 warnings that are explained below and are not server
faults.**

First endurance run against the DTLS stack that ships in 0.5.0. Every earlier
DTLS soak measured `webrtc-dtls` 0.10 as a dependency; this one measures
`crates/dtls`, which changes the handshake state machine (a server whose caller
validated the client address starts at handshake sequence 1). Those runs do not
carry over, which is why this one exists.

## Setup

| | |

`scripts/soak/soak.sh`, analysed by `scripts/soak/analyze.py`.

## DTLS: the result this run was for

Eleven DTLS phases, and they are indistinguishable from each other:

| | |
|---|---|
| Packets per phase | 552 948–552 951 |
| Received | identical to sent, every phase |
| Loss | **0**, every phase |
| Rate | 312.26–312.28 /s |
| Relayed back | 88 MB per phase |
| Handshake failures | 0 |
| Accept timeouts | 0 |
| Sessions established | 96 |

The spread between the first phase (cycle 2, hour 0.6) and the last (cycle 39,
hour 22.9) is **two packets**. There is no drift, and nothing degrades across a
day.

`turna_dtls_cookie_challenges_total` reached 300 against 96 sessions. Every
handshake pays exactly one challenge by design, so three challenges per session
means retransmission: 50 clients start a phase simultaneously and some
HelloVerifyRequests are answered more than once before a session settles. It is
consistent with the 16 `errs` each DTLS phase reports (see below) and with zero
handshake failures — nothing is failing, some clients are asking twice. A
single-client check on the wire would confirm it in a minute and has not been
run.

`turna_dtls_pending_handshakes` stayed at 0 and
`turna_dtls_rejected_pending_cap_total` never moved: no handshake state
accumulated at any point.

## What else passed

- **Allocation release.** 127 884 allocations churned; the idle floor of
  `turna_active_allocations` returned to 0 every cycle. This is the leak class
  that matters most for a relay and it is clean.
- **File descriptors:** 0 → 0. **Threads:** 6 → 6.
- **Flat throughout:** `send_queue_dropped_total`, `malformed_packets_total`,
  `parser_rejections_total`, `processor_panics_total`, `tls_accept_errors_total`,
  `tls_framing_errors_total`, `tls_cert_reload_failures_total`.
- **Readiness:** transport and backend ready for the whole run.
- **`channel-data`:** 5.66 M packets and 928 MB per phase, 3198 /s, zero errors,
  zero loss, p50 around 500 µs.
- **Clean exit.** The run ends with SIGTERM because the drain path is part of
  what is under test; the node drained and exited without complaint.

## RSS: the analyser failed this run, and was wrong

The first analysis reported `FAIL RSS: idle floor 12 MiB -> 14 MiB (+16.8%)`.

The idle floor by elapsed time:

| Elapsed | RSS |
|---|---|
| 30 min | 12.3 MiB |
| 3.4 h | 14.1 |
| 6.4 h | 14.0 |
| 9.3 h | 14.5 |
| 12.2 h | 14.5 |
| 15.2 h | 14.4 |
| 18.1 h | 14.6 |
| 21.0 h | 14.4 |
| 23.9 h | 14.5 |

All of the growth is in the first three hours; the remaining twenty-one are flat
and drift **down** as often as up. A leak does not drift down. Two megabytes
across 127 884 allocations and 60 M packets is pools, allocation maps and port
tables reaching working size.

The analyser compared the minimum of the first half of idle samples against the
second, and on a 24 h run the first half contains the 30-minute sample — a number
the process never returns to. The 15 % threshold was reasoned for a six-hour
run, where the same comparison does not straddle warm-up.

`scripts/soak/analyze.py` now excludes the first two hours from the RSS baseline
(`RSS_WARMUP_SECS`), leaving the threshold alone: raising it would hide a real
leak, which is the opposite of what this signal is for. Re-analysed:
`PASS RSS: idle floor 14 MiB -> 14 MiB (+3.1%), excluding the first 2 h of
warm-up (30 samples)`.

Two hours rather than a fraction of the run, because warm-up is a property of
the process and not of how long you intend to watch it. Runs under six hours keep
the old behaviour.

## The 17 warnings: `allocate` and `binding` error counts

Every `allocate` phase reports ~354 000 errors against ~14 166 successes, every
`binding` phase ~177 200 against ~14 174. Identical across all eleven occurrences
of each.

**These are not server failures.** The server-side counters for the whole run:

| | |
|---|---|
| `turna_rate_limited` | 0 |
| `turna_quota_exceeded_total` | 0 |
| `turna_peer_rejected_total` | 0 |
| `turna_auth_failures` | 2958 |

354 000 rejections would have to appear in one of those. They appear in none.
The first hypothesis was the rate limiter — the soak script raises the limits
through the deprecated `TURNA_RATE_LIMIT_*` variables, so a failed override was
plausible — and `turna_rate_limited 0` rules it out.

The count comes from the load tool. `tools/load-test` increments `errs` on any
request that does not get a reply within its window, and computes
`loss = sent - (recv + errs)`. **`loss` is 0 in every phase**, which is the
useful reading: every packet sent is accounted for, either answered or counted.
The `allocate` mode sends far more requests than it waits for replies to, so a
large `errs` is a property of how that mode drives the server, not a symptom in
the server.

Worth fixing in the tooling rather than here: the analyser's "more failures than
successes" wording invites exactly the wrong conclusion, and a warning that fires
on normal operation trains people to skip warnings.

## Known gaps

This run answers one question: does the node degrade over a day under steady
load. It does not.

It does not answer the other five in
`docs/verification/dtls-stack-2026-09-15.md`, and two of those are blocking for
lifting the beta label:

- **Spoofed-source flood.** The reason the cookie gate was written. Minutes to
  run, and until it is run we know the gate works under honest load and nothing
  about it under attack.
- **Packet loss on a real interface.** The change is in sequence handling, and
  loss is what makes sequence handling matter: a dropped HelloVerifyRequest means
  the client retransmits at `message_seq` 0 while the server has moved to 1.

Also outstanding: three browsers, coturn's client, certificate hot-reload under
live sessions.

## Follow-ups from this run

- `scripts/soak/soak.sh` still exports `TURNA_RATE_LIMIT_*`, deprecated in 0.5.0
  and warned about twice per run. Move it to `[turn.rate_limit]`.
- `allocation created` is logged twice per allocation at INFO — once by
  `turna_session`, once by `turna_relay::processor` — which is 383 652 lines and
  54 MB of `node.stdout` for this run. One of the two should go, and the survivor
  belongs at DEBUG.
- `turna_dtls_cookie_challenges_total` at 3× the session count deserves the
  one-minute wire check before the beta label moves.
