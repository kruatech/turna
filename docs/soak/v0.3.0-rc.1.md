# Soak test — v0.3.0-rc.1

12-hour continuous relay soak of the core UDP/IPv4 datapath on Linux, to verify
absence of memory/fd leaks and stability of packet processing under sustained
load. This closes the "long soak" item for the RC → GA checklist.

## Setup

- Single node (`turna-node deploy/turn.toml`), release build, Linux x86_64.
- Management/health on :9090, TURN on :3478.
- `TURNA_ALLOW_LOOPBACK_PEERS=1` (dev-only override, so the local load client
  could relay to loopback peers; production keeps the peer filter strict).
- Load generator: `turna-load-test` — ChannelData relay, 20 channels, 1000 pps
  per channel, 160-byte payload, duration 43200 s (12 h).
- Sampler: RSS / fd / key counters snapshotted every 30 min (25 samples).

## Results

### Throughput
- Packets sent: 518,400,014 (~12,000 pps sustained, no degradation over 12 h;
  first 30-min window 21.15M packets, last window 21.60M).
- Relayed: 79.18 GiB out / 1.07 GiB in.

### Memory — no leak
- RSS started at 7,516 kB (cold start), warmed to ~11 MB within the first
  30 minutes, then oscillated in a 10,048–11,704 kB band for the remaining
  12 hours (spread ~1.6 MB). First warm sample 11,196 kB, last sample
  11,216 kB — effectively flat across 518M packets. No upward trend.

### File descriptors — no leak
- fd count = 42 in all 25 samples, zero deviation.

### Processing — clean
- `turna_processor_panics_total` = 0 in every sample.
- `turna_send_queue_dropped_total` = 0 in every sample (no send-queue
  backpressure at 12k pps on this stand).
- `turna_parser_rejections_total` = 0, `turna_malformed_packets_total` = 0,
  `turna_quota_exceeded_total` = 0, `turna_peer_rejected_total` = 0.
- `turna_auth_failures` = 12 (load client handshake/startup; correlates with the
  8 startup errors + retries, does not grow during the run).

### Errors
- Load client: 8 errors out of 518.4M sends = 0.00%. All 8 occurred at startup
  (present at the 1-minute mark); zero new errors in steady state.

### Latency
- Min 26 µs, Avg 170 µs, P50/P95/P99 500 µs, Max 15,837 µs.
- Distribution: ~99.6% of packets under 500 µs (1,261,689 < 100 µs;
  5,914,956 < 500 µs). Tail is tiny: 256 packets in 10–50 ms, and ZERO packets
  above 100 ms across the whole run. The 15.8 ms max is a single outlier, not a
  trend.

## DoD — met

| Criterion              | Result                                   |
|------------------------|------------------------------------------|
| Duration               | 12 h continuous                          |
| Volume                 | 518M packets, 79 GiB relayed             |
| Memory leak            | none (RSS flat ~11 MB)                    |
| fd leak                | none (42 stable)                         |
| Processor panics       | 0                                        |
| Send-queue drops       | 0                                        |
| Error rate             | 0.00% (8 startup, 0 in steady state)     |
| Latency P99            | 500 µs                                   |
| Degradation over time  | none (throughput flat)                   |

## Limitations

- Ran over loopback with the dev peer-filter override. This proves absence of
  leaks and stability of packet processing under sustained volume; it does NOT
  exercise real-network dynamics (NAT, packet loss, jitter, MTU). Real-network
  load remains a separate GA item.
- Single node; cluster/persistence paths are covered by the failover drill
  (see docs/failover/v0.3.0-rc.1.md), not by this soak.
- ~12k pps on one stand; higher-scale and many-allocation behaviour is a
  separate GA item.
