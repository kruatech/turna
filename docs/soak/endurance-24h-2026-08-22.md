# 24-hour endurance — TURNS and io_uring — 2026-08-22

Ubuntu 24.04, kernel **6.8.0-87**, 4 cpus, 8 GiB. Traffic over the public interface to
`turna.quinter.ru:5349` with the deployment's real Let's Encrypt certificate — not
loopback and not a self-signed test cert.

| Phase | Duration | Result |
|---|---|---|
| TURNS, relayed media | 9.6 h | 16 cycles × 138 040 frames, **zero loss** every cycle, 22 MB relayed per cycle |
| TURNS, allocation churn | 4.8 h | 8 cycles, 6 516 330 allocations, 441/s, p99 100 ms |
| io_uring, relayed media | 9.6 h | 16 cycles × 702 040 of 702 080, **0.006 % loss**, zero errors |

**No leak on any signal.** RSS idle floors 10 → 11 MiB (TURNS media), 12 → 12 (churn),
132 → 132 (io_uring). File descriptors 19 → 19 and 18 → 18. Threads 5 → 5 and 13 → 13.
Every error counter flat: dropped, malformed, parser rejections, TLS accept and framing
errors, certificate reload failures, processor panics. Readiness stable throughout on
the transport, backend and TLS listeners.

The only failing signal in each phase was one empty `load-*.json`: the rotation starts a
cycle whenever one is due, so the final one began with less than a window left and was
cut off before writing. A harness artefact — the analyser now reports it as a warning
when it is the last file and still a failure anywhere else, because an empty file
mid-run means a phase died.

## What this run had to fix first, and why it matters

Two earlier 24 h attempts produced 67–68 % loss on **every** transport at **every**
rate, which read like a capacity cliff on a small host. It was not.

**TURN bindings expire and the load client never refreshed them.** An allocation lasts
600 s (RFC 8656 §7.2), a permission 300 s (§9), a channel binding 600 s (§11.2). The
client bound once and then sent for 1755 s. Past the deadline the server is *required*
to drop ChannelData for a binding that no longer exists, and it did so silently — there
is no error to receive when you are talking to a channel that is gone.

The arithmetic is what settled it:

| Phase | Duration | Predicted 600/duration | Observed delivery |
|---|---|---|---|
| rehearsal, TURNS | 244 s | 1.000 | 1.000 |
| rehearsal, io_uring | 244 s | 1.000 | 1.000 |
| 24 h, TURNS | 1755 s | 0.342 | 0.325 |
| 24 h, io_uring | 1755 s | 0.342 | 0.325 |

Identical on two unrelated transports, and matching a formula that has nothing to do
with CPU. Rehearsals passed clean because 244 s never reached the deadline — which is
exactly what made it look like concurrency mattered.

**The consequence reaches backwards.** Every long `channel-data` phase run before this
fix was measuring a decaying session: correct for the first ten minutes, then relaying
into a closed channel. The three-hour soaks recorded earlier are affected and their
throughput figures should not be quoted. Their *leak* findings stand — a datapath that
forwards nothing still would not have leaked.

Both clients now refresh every 240 s, inside the shortest of the three deadlines. The
fix was verified on a 676 s phase (past 600, zero loss) before this run, and this run
confirms it at 1755 s.

**The analyser now recognises the signature**: when delivery matches `600/duration`, it
names an expired binding instead of suggesting a capacity comparison. The old advice —
"compare against a lower rate" — was wrong, because the tell here is duration, not rate.

## Two harness faults found on the way

**Metrics were scraped from the wrong process.** `overnight.sh` set the health port in
the node's config but not in `HEALTH_ADDR`, which `soak.sh` reads directly and defaults
to `127.0.0.1:9091`. An unrelated Go process held that port, so an entire 24 h run
reported "series absent from /metrics" for every `turna_*` check and told us nothing.
The script now refuses to start if the health port is held by something else.

**A phase that relayed a third of what it sent read as a pass.** The load-phase check
looked at `recv > 0` and `errs == 0`, both true, while `loss` sat in its own field and
nothing looked at it. Loss and error rates are now always stated.

## Scope

- **One kernel.** 6.8 here; 6.14 is on record separately
  (`docs/soak/endurance-2026-08-19.md`). io_uring is version-sensitive, so this is
  evidence about these two kernels and no others.
- **Chain validation is not what this measured.** The certificate was real, but the load
  client accepts any certificate by design. Validation is proven by a verifying client —
  `openssl s_client -verify_return_error` against this deployment returned
  `Verify return code: 0`, recorded separately.
- **Modest rate, deliberately.** 20 TLS sessions at 10 pps and 40 UDP channels at 10 pps
  on a 4-cpu host. Endurance measures degradation over time; a rate near saturation
  turns every later signal into noise about the saturation, which is precisely what
  happened on the first attempt.
- **No independent implementation** — this is the load client, which shares a library
  and one reading of the spec with the server. For TURNS that gap is covered by the
  three-browser interop; this run is endurance, not interop.
