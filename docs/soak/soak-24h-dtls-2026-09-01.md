# 24-hour soak, DTLS demux path — 2026-09-01

**PASS. No leak, and the demux path held for a full day.**

This is the run the `demux = true` decision was waiting on.
`scripts/verify/dtls-demux.sh` had already shown the path correct — nine checks of
nine, including both §7 P0 requirements the stock listener cannot provide. What it
could not show is stability, and those are different claims: the io_uring path
went deaf after exactly 64 packets, and AF_XDP stopped receiving after exactly
2015 frames. Neither would appear in five minutes.

|---|---|---|
| RSS | 16 MiB | 18 MiB |
| File descriptors | 20 | 20 |
| Threads | 6 | 6 |

Across 24.02 hours: **303 403 771 allocations**, **4 034 831 916 packets**, zero
processor panics, and `turna_send_queue_dropped_total` **flat** — not a single
egress drop, where the previous soak had 467.

**The node exited cleanly on SIGTERM.** Worth stating on its own: before the
runtime-shutdown fix it never did, and every earlier soak ended with a SIGKILL
that hid it.

**Identical to three significant figures across twenty-four hours**, spread of 16
frames in 1.7 million. That flatness is the result: a path that leaks or degrades
does not repeat itself this closely on the eleventh pass.

Fifty errors per cycle, in every cycle, at `-c 50` — one per session, and the same
number whether the cycle ran at hour one or hour twenty-three. That shape says
teardown when the driver stops rather than a fault in steady state. Worth
confirming, and it is not a degradation: a fault that accumulated would not hold
at exactly 50.

## The eleven warnings

All the same cause. `allocate` phases reported 26–32 % errors; `channel-data`
reported zero and `binding` 0.04 %.

The soak drives `allocate --concurrency 400` from a single source address, and
`TieredLimits::allocate` is 32 per second per IP with a burst of 16. So roughly
one in three attempts is refused, by design, and `p99` of 100 ms on those phases
is time spent waiting on the limiter rather than latency in the relay — the other
phases sit at 5 ms.

The proportion rose from 18 % in the previous soak to about 30 % here because the
DTLS cycles added contention for the same cores. The load tool has `--source-ips`
for exactly this; the soak script does not use it, which is worth fixing so that
these phases measure the node rather than the limiter.

## What this establishes for the demux default

Both §7 P0 requirements are confirmed on the demux path and are structurally
unavailable on the stock one — `listen()` fixes its certificate at bind time, and
the handshake completes below `accept()` where nothing can rate-limit it.

Correctness: 9 of 9, `scripts/verify/dtls-demux.sh`.
Stability: 24 hours, this run.
Shutdown: exits cleanly on SIGTERM.

The stock path's claim to being the default was a recorded 24-hour run. The demux
path now has one too, and it has the two things the stock path cannot do.

## What it still does not establish

**A real NIC.** Loopback, one host, driver and node sharing the cores. DTLS
handshakes over a network add packet loss during the handshake, which is where a
demultiplexer is most likely to differ from a listener that owns its socket.

**Handshake rates a deployment would see.** 50 concurrent sessions held open for
the phase, not churned. The per-IP handshake limiter was verified separately, at
3/s from one address.

**Certificate rotation over 24 hours.** `cert_reload_secs = 300` was set, so the
reloader ran roughly 288 times, and `turna_tls_cert_reload_failures_total` stayed
flat — but the certificate file never changed, so that is the no-op path rather
than a rotation.
